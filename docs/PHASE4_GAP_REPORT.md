# Phase 4 Gap Report: Metrics & Charts

## Audit summary

This audit is read-only and intentionally does not modify application code, endpoints, or database schemas. It checks the repository state against the Phase 4 requirements in [docs/IMPLEMENTATION_PLAN.md](docs/IMPLEMENTATION_PLAN.md), [docs/ACCEPTANCE_CRITERIA.md](docs/ACCEPTANCE_CRITERIA.md), and [docs/API_SPEC.md](docs/API_SPEC.md).

## Confirmed findings

### 1) The dashboard is still a placeholder, not a live metrics page

The live route for the dashboard in [frontend/src/App.tsx](frontend/src/App.tsx) still renders a `PlaceholderPage` for `/dashboard` rather than a real metrics screen. The route description explicitly labels the phase as “Phase 4” and lists the acceptance criteria as text, but there is no data-fetching logic, KPI card set, chart rendering, or empty-state handling.

The same gap is visible in [frontend/src/pages/PlaceholderPage.tsx](frontend/src/pages/PlaceholderPage.tsx), which is a static scheduled-page component and not a real dashboard implementation.

### 2) There is no backend metrics endpoint or shared metrics service

The current API routes in [backend/app/api/trials.py](backend/app/api/trials.py) expose create/list/get/update operations and CSV preview/import only. There is no `GET /api/trials/{trial_id}/metrics` route, no endpoint response model, and no stored metric payload in the response contract.

The backend services package includes only audit, auth, participant, and trial logic. No service named for metrics or deterministic status aggregation is present. The only participant service file is [backend/app/services/participant_service.py](backend/app/services/participant_service.py), which validates and imports CSV rows but does not compute totals, rates, or quality flags.

### 3) The data model supports participant statuses but not aggregate calculations

The participant model in [backend/app/models/participant.py](backend/app/models/participant.py) stores a normalized `status` field and optional date/visit metadata. This is sufficient for a backend aggregate service to compute counts, but the model is not yet paired with a metrics service or query helper.

The trial model in [backend/app/models/trial.py](backend/app/models/trial.py) establishes the ownership and participant relationship, but there is no aggregate metric result model or helper function for status distribution.

### 4) CSV import validation is implemented, but there is no downstream metrics logic

The CSV import service in [backend/app/services/participant_service.py](backend/app/services/participant_service.py) performs file validation, required column checks, status normalization, duplicate detection, and transaction-safe import. However, this service only validates rows and records import metadata; it does not compute totals or any trial-level summary metrics after import.

The import response contract in [frontend/src/api/client.ts](frontend/src/api/client.ts) also contains only preview/import payloads and does not include a metrics contract.

### 5) The codebase has no empty-state or data-quality handling for metrics

The UI specification in [docs/UI_UX_SPEC.md](docs/UI_UX_SPEC.md) clearly requires KPI cards, accessible chart labeling, empty-state handling, and a warning if status counts do not reconcile, but no matching implementation exists in the current frontend.

There are no data-quality flags in the backend schema, no warning banner components in the UI, and no reconciliation logic such as `status_counts_reconcile` or `data_quality` response payloads.

### 6) Acceptance criteria AC-030 through AC-034 are not yet satisfied by current code

These criteria are defined in [docs/ACCEPTANCE_CRITERIA.md](docs/ACCEPTANCE_CRITERIA.md):
- AC-030: 120 participants with 95 completed, 15 withdrawn, 10 active must total 120 and compute to 79.17%, 12.50%, and 8.33%.
- AC-031: counts must be computed by backend code, not generated by AI.
- AC-032: empty trials must show an empty state and not divide by zero.
- AC-033: inconsistent status counts must surface a data-quality warning.
- AC-034: chart labels and text summaries must explain the breakdown without relying on color alone.

Current evidence:
- No metrics endpoint or service exists.
- No dashboard chart component exists.
- No zero-state logic or quality-warning logic exists.
- No backend test or frontend component coverage matches these expected behaviors.

### 7) The implementation should be designed for reuse by both the dashboard and future PDF generation

The architecture section in [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) explicitly states a shared service should compute metrics once and reuse them across dashboard and PDF, but the repository does not yet contain that service. This is a gap against the planned architecture and against the “single metrics service” requirement in [docs/IMPLEMENTATION_PLAN.md](docs/IMPLEMENTATION_PLAN.md).

## Missing requirements and gaps to close

1. A dedicated backend metrics service, likely in the services layer, should compute:
   - total participants
   - completed, withdrawn, active counts
   - completion_rate, withdrawal_rate, and active_rate
   - denominator-safe zero handling
   - consistency flags for `status_counts_reconcile`
   - definitions metadata for UI and PDF reuse

2. A metrics API route should return all values in a deterministic schema that matches the contract in [docs/API_SPEC.md](docs/API_SPEC.md).

3. The dashboard route should replace the placeholder with actual KPI cards, chart components, and accessible textual summaries.

4. The UI should include an empty state for zero-participant trials and a warning banner when count reconciliation fails.

5. A shared response contract should be used for both the dashboard and future PDF export so values match exactly.

6. Regression tests must be added for the exact fixture in AC-030, empty trials, inconsistent counts, and text-only chart explanation.

## Proposed implementation steps

1. Add a backend metrics service that queries participants for the selected trial and aggregates counts by status using deterministic Python logic.
2. Add a `/api/trials/{trial_id}/metrics` endpoint that returns counts, rates, definitions, and `data_quality` metadata.
3. Ensure the service guards against divide-by-zero by returning zero rates when the total is zero and a clear empty-state flag/message.
4. Add reconciliation logic that checks whether the counts sum to the total and set `status_counts_reconcile` to false when the totals do not match.
5. Build KPI cards and a status chart on the frontend using the backend response, with labels and summaries that remain understandable without relying on color alone.
6. Reuse the same backend metric payload for future PDF generation so report totals match the dashboard exactly.
7. Add tests covering normal, empty, and inconsistent data scenarios before implementation is considered complete.

## Test cases to add

### Backend tests
- AC-030 fixture: total 120, completed 95, withdrawn 15, active 10 → completion 79.17, withdrawal 12.50, active 8.33.
- Empty trial: total 0, rates all 0, no divide-by-zero error, empty-state signal/message.
- Inconsistent totals: counts sum to 110 when total is 120 → `status_counts_reconcile` false and warning payload present.
- Metrics endpoint authorization: only same-user access allowed.
- Metrics endpoint uses backend-calculated values, not AI-generated values.

### Frontend tests
- KPI cards render for normal and empty datasets.
- Empty-trial state displays appropriate instruction and CTA.
- Warning banner appears when reconciliation fails.
- Chart text summary lists counts and percentages without relying on color semantics.
- Alert/label text remains readable by screen readers and non-color users.

## Conclusion

The repository is ready for Phase 4 implementation in principle, but the required metrics, charting, empty-state, and data-quality behavior is not yet present. The missing work is specific and scoped: add one deterministic backend metrics service, expose it through the API, and render the resulting values in a real dashboard that matches AC-030 through AC-034.

The project was approved for implementation and the Phase 4 work described above has now been completed with verification evidence.
