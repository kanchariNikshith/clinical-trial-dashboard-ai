# Database Schema

## General rules
Use PostgreSQL, SQLAlchemy 2.x, and Alembic migrations. Use UTC timestamps for stored event timestamps. Store dates as dates where time-of-day is not meaningful. Avoid direct identifiers and real participant data in demo fixtures.

## 1. users
| Column | Type | Rules |
|---|---|---|
| id | UUID or integer PK | Generated by DB/app |
| email | varchar | Required, normalized, unique |
| password_hash | varchar | Required; never plaintext |
| is_active | boolean | Default true |
| created_at | timestamptz | Required |
| updated_at | timestamptz | Required |

## 2. trials
| Column | Type | Rules |
|---|---|---|
| id | UUID or integer PK | Generated |
| owner_user_id | FK users.id | Required |
| trial_code | varchar | Required; unique per owner or globally, decision must be consistent |
| trial_name | varchar | Required |
| status | varchar/enum | Proposed values: planned, recruiting, active, completed, suspended |
| start_date | date | Optional/required per UI decision |
| end_date | date | Optional; cannot precede start_date |
| created_at | timestamptz | Required |
| updated_at | timestamptz | Required |

Recommended MVP uniqueness: `(owner_user_id, trial_code)` so different demo users can use the same code.

## 3. participants
| Column | Type | Rules |
|---|---|---|
| id | UUID or integer PK | Internal key |
| trial_id | FK trials.id | Required |
| participant_code | varchar | Required synthetic/study code; not a person's name |
| status | varchar/enum | active, completed, withdrawn |
| visits_completed | integer | Optional, >= 0 |
| visits_planned | integer | Optional, >= 0; if both present, completed <= planned |
| enrollment_date | date | Optional |
| last_visit_date | date | Optional |
| next_visit_due_date | date | Optional; only used for operational reminders when a rule is defined |
| created_at | timestamptz | Required |
| updated_at | timestamptz | Required |

Unique constraint: `(trial_id, participant_code)`. Do not store participant name, email, DOB, address, medical record number, or raw medical measurements in MVP.

## 4. audit_events
| Column | Type | Rules |
|---|---|---|
| id | UUID or integer PK | Generated |
| actor_user_id | FK users.id, nullable | Null may be used for unauthenticated login attempts; minimize IP retention |
| action | varchar | Controlled action name |
| entity_type | varchar | e.g. trial, import, report, ai_analysis, auth |
| entity_id | varchar, nullable | Internal identifier only where useful |
| outcome | varchar | success/failure |
| occurred_at | timestamptz | Required |
| metadata_json | JSONB, nullable | Allowlisted non-sensitive metadata only |

Never put passwords, bearer tokens, API keys, raw CSV content, prompts containing participant rows, or unnecessary health data into audit metadata.

## 5. Optional import_batches
Add only if import history/status is needed:
- id, trial_id, uploaded_by_user_id, original_filename (sanitize; optional), row_count, imported_count, rejected_count, status, created_at.
Do not persist file contents by default.

## Relationships
- One user owns many trials.
- One trial has many participants.
- One user creates many audit events.
- A trial may have many import batches if that optional feature is approved.

## Indexes
- Unique index on users.email.
- Unique index on trials `(owner_user_id, trial_code)`.
- Unique index on participants `(trial_id, participant_code)`.
- Index participants.trial_id and participants.status.
- Index audit_events.occurred_at and audit_events.actor_user_id.

## Migration requirements
- Create schema using Alembic migrations.
- Test a fresh database migration and upgrade from the prior migration.
- Do not alter production schema manually.
